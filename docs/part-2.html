Nothing Catches Everything

Scanner vendors lead with detector counts. Miss rates are far harder to find. So I measured one: six tools, one synthetic corpus, one secret caught by nothing.

Part 2 of 4 · Engineering Research current to August 2026 ~8,700 words · 39 min

Before the engineering: why anyone is paying for this

If you are an engineer being asked to stand up secret scanning, this is the argument that funded the request. It is compressed from Part 1. Skip it if you already have the budget.

  1. A leaked credential reaching a public surface is exploited in under sixty seconds by automated harvesters watching commit streams.1 Anything downstream of the push is a race you have already lost — which is why placement matters as much as tool choice.
  2. The volume is not falling. GitGuardian counted 28.65 million hardcoded secrets reaching public GitHub in 2025, up 34 percent year on year, with AI-service credentials up 81 percent.2
  3. Detection is not the failure. Revocation is. GitGuardian found 64 percent of secrets confirmed valid in 2022 were still valid in January 2026.2 Scanning, validity checking, revocation and credential architecture are four different control types; Part 1 separates them. Your scanner's job is to feed a remediation pipeline, not to be one.
  4. All three of the exposures examined in part one — selected for structural variety, not for size — turned on credentials that no repository scanner would have flagged — one was an issued OAuth token, one was a publishing token sitting in a CI runner's environment, and one campaign used a secret scanner as its harvesting tool.3
  5. Even within its own remit, no scanner is complete. Against a purpose-built corpus of 41 synthetic secrets, the best of six selected scanners reached 95 percent recall, all six together reached 40 of 41, none caught anything the other five missed, and one secret was caught by nothing.28 Section four has the run.
  6. Regulation now names this explicitly. PCI DSS v4.0.1 requirement 8.6.2 prohibits hardcoded passwords in scripts, configuration files and source code, and became mandatory on 31 March 2025.4 Part 4 covers the full mapping.

So the engineering question is not "should we scan." It is narrower and more useful: which detection techniques exist, which tool implements which, where do you install it, and how do you find out what it misses before an attacker does.

Section one · Mechanism

Five detection techniques, and what each one cannot see

"Secret scanner" describes a category, not a technique. Every tool in the category is some combination of the five approaches below, and the combination determines both what it finds and how much noise it generates. Choosing a tool without knowing which techniques it implements is how programmes end up with 90 percent of their alerts being test fixtures.

Keep one distinction in view throughout, because it decides what any of this is worth: detection technique and control type are independent axes. The same tool is a preventive control at the pre-commit or pre-receive boundary and a detective one everywhere downstream. Validity checking is neither — it prioritises. Revocation is the only corrective step, and short-lived, scoped, workload-bound identity is preventive architecture that operates on a different plane entirely. Part 1 has the full taxonomy; this section is about the techniques inside the box.

1
Pattern match

What it does. Regular expressions matched against known provider token formats — AKIA for AWS long-lived keys, ghp_ for GitHub personal access tokens, sk_live_ for Stripe. Fast, deterministic, and the backbone of every tool in the category.

What it cannot see. Anything without a distinctive shape. A database password in a connection string, an internal service API key with no vendor prefix, a private key pasted without its PEM header. This is the largest single blind spot in the category, and it is structural rather than a bug: you cannot write a regex for "arbitrary string that happens to be a password."

2
Entropy

What it does. Shannon entropy over base64 or hexadecimal strings, on the theory that a random-looking 40-character string in a config file is probably a key. This is the only technique that has any chance at unstructured secrets.

What it cannot see, and what it wrongly sees. Entropy is a proxy, not a test. It misses low-entropy secrets (password: Summer2026!) entirely, and it flags every UUID, git SHA, content hash, minified asset, base64-encoded image and test fixture in the tree. Basak and colleagues identified "ineffective entropy calculation" as one of the two root causes of false positives across the nine tools they evaluated.5

3
Keyword and context

What it does. Looks at the surrounding code rather than the string alone: an assignment to a variable named api_key, a key called password in a YAML map, proximity to a known provider's SDK import. Yelp's detect-secrets ships a dedicated keyword detector alongside its regex plugins.6

What it cannot see. Secrets in data rather than code — a credential inside a JSON blob, a log line, a fixture file, a Jupyter output cell. It also inherits the naming conventions of whoever wrote the code; a variable called cfg7 defeats it.

4
Structural validation

What it does. Checks internal consistency without contacting anyone. GitHub's token formats embed a CRC32 checksum in the final six characters; GitHub states that the prefix alone drops the false positive rate to 0.5 percent and the checksum "virtually eliminates false positives for secret scanning offline."7 This is the cheapest precision improvement available and only some tools implement it.

What it cannot see. Only works where the provider designed a checksum in. Notably, AWS access key IDs have no checksum — the format is a four-character prefix plus sixteen characters of custom base32, and altering the trailing characters does not invalidate it.8 Most providers offer nothing to validate against.

5
Live verification

What it does. Calls the provider's API to ask whether the credential still works — sts:GetCallerIdentity for AWS, and equivalents elsewhere. TruffleHog made this its defining feature and classifies every finding as verified, unverified or unknown.9 It converts a probabilistic finding into a fact, and it is the single most useful signal for triage priority.

What it cannot see, and the trap. It cannot help with a secret whose provider has no verification endpoint, and it says nothing about a credential that was valid last week and has since rotated but is still in history. The trap: GitGuardian's research found that prioritising by validity alone missed 46 percent of critical secrets.2 Verification is a triage input, not a filter.

Scan surface is a separate axis from technique

A tool with excellent detection installed in the wrong place is worth very little. Four surfaces matter, and most tools support only some of them:

  • Working tree only. Scans what is checked out now. Fast, suitable for pre-commit. detect-secrets works this way by design, explicitly avoiding "the overhead of digging through all git history."6 If your benchmark plants secrets in old commits, a working-tree scanner scores zero by design, not by failure.
  • Full git history. Walks every commit on every branch. This is the only way to find the secret that was committed and then "removed" in the next commit — which is still in the pack file and still readable. Gitleaks, TruffleHog, Kingfisher and Titus all do this.
  • Push time. Evaluated between git push and the object landing on the server. This is the only genuinely preventive placement, and it belongs to the platform, not to a CLI.
  • Everything that is not a repository. Ticket systems, wikis, chat, container image layers, CI logs, IaC state files, MCP configuration. GitGuardian put 28 percent of incidents in collaboration tools specifically — Slack, Jira and Confluence.2 The other surfaces in that list are real and unmeasured here; do not read the 28 percent as covering them.2 No CLI git scanner addresses any of it.

There is a fifth surface, and it is not a surface these tools have a bad score on — it is one they cannot address in principle. Repository and artifact scanners do not detect credentials that exist only at runtime. A stolen session cookie, a token scraped out of process memory, a credential minted dynamically by a workload identity broker, a value read from an instance metadata service: none of these is ever written to a file that a scanner walks, so no amount of ruleset coverage, history traversal or entropy tuning will surface them. Detecting that class requires identity, endpoint and workload telemetry — anomalous token use, impossible-travel and unusual-ASN signals on API calls, process-level access to credential stores, egress from a workload to an endpoint it has never called. Expanding static scan coverage does not close a runtime-credential gap, and a programme that reports scanner coverage as its credential-risk metric is measuring the surface it can see rather than the one that is being attacked. Part four returns to this as a governance question; the point here is a scoping one, and it bounds every number in this article.

Section two · Selection

Detector count is the metric vendors lead with and the least informative one available. Eight hundred detectors weighted toward services you do not use is worth less than forty covering the ones you do. Evaluate against the criteria below, in roughly this order of importance.

Section three · Landscape

What is available, and what changed in 2026

Four things shifted in this category recently, and a comparison written even a year ago now misleads on all four.

  • Gitleaks is feature-frozen. Its README describes the project as feature complete with new features not being merged. The original author has started a successor, Betterleaks, which adds the live verification Gitleaks never had.1011
  • The Gitleaks CLI and its GitHub Action have different licences. The CLI is MIT. gitleaks-action has been proprietary since v2.0.0 and requires a licence key — free, but a key — for organisation-owned repositories.12 This is the detail most comparison articles get wrong.
  • Nosey Parker was archived in April 2026 and replaced by Praetorian's Titus.13 If your pipeline still references it, it is running a frozen ruleset.
  • GitHub unbundled Advanced Security. From 1 April 2025, secret scanning for private and internal repositories is sold separately as GitHub Secret Protection at $19 per active committer per month. Public repositories keep it free, including full history across all branches.1415

Commercial — listed, not benchmarked

These require a paid account for meaningful use, so they are excluded from the benchmark in the next section. That is a limitation of the method, not a judgement on the products — and it is worth saying plainly that the tool with the highest measured precision in the peer-reviewed study was a commercial one.

  • GitGuardian — the most generous free tier of the commercial set: the Starter plan covers up to 25 developers, 1 GB scanned, 500 historical detections. Caveat, unresolved: GitGuardian's pricing page lists "no CI/CD scanning" as excluded from Starter, while the ggshield documentation describes service accounts for CI pipeline scanning. These two primary sources appear to conflict; verify with a free account before assuming ggshield is free-tier testable in Actions.19
  • Aikido Security — free Developer plan at $0 for 2 users and 10 repositories, with secrets detection, liveness detection and pre-commit blocking included; rescans every three days.20 On those limits it is arguably testable, though not at organisation scale.
  • Semgrep Secrets — not in the open-source edition. Semgrep CE is LGPL-2.1 and covers SAST only; the free tier is 10 repositories and 10 contributors, without Secrets.21
  • Snyk — a Snyk Secrets product exists; the public plans page does not state whether it is included in the free tier. Verify before relying on it.
  • Wiz Code and Cycode — no public pricing; paid only. Both correlate secrets to cloud blast radius rather than treating a finding as a file-level event, which is genuinely different from a CLI scanner.
  • NHI platforms — Entro, Astrix, Oasis, Clutch. These start from the identity rather than the file: inventory service accounts, API keys, OAuth apps and tokens across SaaS and cloud, then attach ownership, permission scope, rotation age and usage telemetry. If your problem is "we do not know what machine identities exist," a repository scanner is the wrong tool entirely.
Section four · Measurement

Build a corpus and find out what yours misses

I found no current independent benchmark of these tools with comparable reproducibility — one that publishes its corpus, its seed, its ground truth and its scoring so that a reader can regenerate the whole thing and check the arithmetic. Searching returned vendor blogs and listicles with no reproducible methodology. That is a statement about what a search surfaced, not a proof that nothing exists; if there is one, I would rather cite it than repeat the work. The last peer-reviewed comparison is the 2023 ESEM study,5 which predates Betterleaks, Kingfisher, Titus, and every AI-service credential format.

So this section is now a report rather than a proposal. The design below was built as secret-scanner-benchmark: it plants a synthetic corpus with known ground truth, assembles it into a git repository with deterministic history, runs six free and self-hostable scanners against it in CI, and scores precision and recall overall, per secret type and per placement.28 The results are in this section. Read the limitations before the numbers — one of them substantially qualifies what a benchmark of this shape can measure.

Why not just use SecretBench

SecretBench is the obvious starting point — 97,479 candidate secrets from 818 public repositories, of which 15,084 are labelled true secrets.22 Two reasons to build your own instead, and one reason to still read it:

  • It is heavily duplicated. A 2026 analysis found SecretBench is 69.3 percent exact duplicates and only about 22 percent unique, and that removing duplicates dropped a Random Forest classifier's MCC from 0.89 to 0.65 — concluding that reported performance "may reflect memorization rather than true learning."23 That paper evaluates ML classifiers rather than the CLI tools, so do not transfer its numbers to Gitleaks or TruffleHog. But it is a strong current argument that the standard corpus is contaminated.
  • Its secrets came from real repositories. The liveness status of those credentials is not something to assume. If you use it, read the ethics section of the paper first.
  • It still tells you the shape of the answer, and the companion false-positive dataset FPSecretBench gives raw FP counts per tool over the same repositories — from 429 for GitHub's scanner to over 1.5 million for one commercial tool.24

Corpus design

The corpus should be a matrix, not a list. Three dimensions, each of which independently defeats some tools:

  • Secret type. Structured with checksum (GitHub tokens), structured without checksum (AWS, Stripe, Slack, SendGrid), PEM private keys, JWTs, cloud service account JSON, database connection strings, AI service keys (OpenAI, Anthropic, HuggingFace, DeepSeek), and generic high-entropy strings with no provider identity at all.
  • Placement. Current working tree; a commit five deep in history; a commit that was later reverted; a non-default branch; a .env file; a JSON fixture; a Jupyter notebook output cell; a Dockerfile ENV; a Terraform variables file; a CI log artifact; a minified JS bundle; inside a base64-encoded blob.
  • Obfuscation. Plain; string-concatenated across lines; stored in a variable named something meaningless; split across an array; with the value on the line after the key.

Include a control group of realistic decoys — UUIDs, git SHAs, content hashes, base64 images, documentation example keys, provider-published placeholder values. Precision is meaningless without them, and a tool that flags every UUID will look excellent on a corpus containing only real secrets.

Three design choices are worth naming because they determine what the numbers mean:

  • The manifest is moved out of the scan target before scanning. It holds every planted value in plaintext; leaving it in place inflates every tool's recall to nearly 100 percent and measures nothing.
  • The seeded generator is a Mersenne Twister, deliberately not a CSPRNG. The output must be predictable and regenerable, which is the opposite of what you want when minting a real credential — and a useful reminder that these values are not credentials.
  • GitHub tokens are planted in matched valid/broken checksum pairs — the experiment proposed earlier in this section, to separate checksum-aware tools from regex-only ones.

The workflow, and one guard worth copying

The workflow implements the constraints listed earlier: one job per tool with fail-fast: false, fetch-depth: 0 so history-capable tools see history, TruffleHog run twice to demonstrate the verification trap, SARIF or JSON per tool uploaded as an artifact and scored against the manifest, every action and tool pinned to an exact version, and no repository secret injected into any job — the corpus is the only input.

It also carries a guard that is not obvious until you need it: the generate job fails the run if the committed manifest is stale, by regenerating the corpus from the seed and comparing the resulting HEAD commit against the recorded one. Without that check, a corpus edit silently scores every tool against the wrong ground truth and the run still goes green. Two tools are excluded and the reasons are recorded: git-secrets has no structured output to parse, and GitHub secret scanning is a platform feature rather than a CLI — though its push protection does fire on this corpus.

Generating synthetic secrets without creating real ones

This is the part that goes wrong quietly. Five rules:

  1. AWS keys have no checksum, but they do encode an account ID. The format is a four-character prefix (AKIA long-lived, ASIA temporary) plus sixteen characters of a custom base32 alphabet, and altering the trailing characters does not invalidate it — there is no validation mechanism. But characters five to thirteen encode the AWS account ID for keys issued since about March 2019, recoverable entirely offline.8 Generate from an obviously invalid account number rather than at random.
  2. GitHub tokens have a CRC32 checksum — use it as an experiment. Prefix (ghp_, gho_, ghu_, ghs_, ghr_), base62 body, and a CRC32 checksum in the last six characters.7 Generate two variants of each: one with a correct checksum and one deliberately broken. Tools implementing the checksum reject the broken one; naive regex tools flag both. That single test cleanly separates checksum-aware from regex-only scanners, and no other test does it as precisely.
  3. Use test-mode formats where the provider offers them. Stripe documents sk_test_ against sk_live_, and publishable pk_ keys as safe to expose.25 A collision with a real test key exposes a sandbox.
  4. Do not build the corpus only from provider "example" keys. Scanners ship allowlists for documentation samples, so the tool will correctly ignore them and you will misread that as a false negative. Use them deliberately, in the decoy group, where being ignored is the correct behaviour.
  5. Plant one canary as a tripwire. An AWS canary token is a fabricated credential that alerts if anyone ever authenticates with it.26 It is not bulk corpus material, but one in the repository tells you if your synthetic secrets ever end up somewhere they should not.

Two further practices. First, generate from a seeded deterministic PRNG and commit the seed, so anyone can regenerate the corpus byte-for-byte and check your scoring. Resist the instinct to reach for a cryptographically secure generator here: unpredictability is exactly what you do not want, and a plain Mersenne Twister makes the point to a reader that these values were never meant to be credentials. (Seeding a CSPRNG is also reproducible, so this is a signalling choice rather than a correctness one — but signal it.) Second, harvest cross-tool: every one of these tools ships test fixtures of format-valid, non-functional secrets, but a tool passes trivially on its own fixtures, so use each tool's fixtures to test the others.

Scoring, and the trap that invalidates most benchmarks

Score against the manifest: true positive, false positive, false negative, then precision, recall and F1 per tool, and again per secret type and per placement. The per-type breakdown is where the useful answer lives — an aggregate F1 tells you almost nothing actionable, while "no tool in the set detected our internal service credential format" tells you exactly what to do on Monday.

The trap. Every synthetic secret in your corpus is, by construction, not live. TruffleHog, Betterleaks, Kingfisher and Titus will therefore classify every one of them as unverified. TruffleHog's own recommended Action snippet runs with verified results only. Run a verification-capable tool that way against a synthetic corpus and every single secret scores as a miss — producing a benchmark that is not merely imprecise but exactly backwards. Run both modes. Report both. This is the most likely way to publish a badly wrong result.

Two further honesty requirements: report N/A rather than a miss for a tool that structurally cannot see a placement — detect-secrets scoring zero on history-planted secrets is a design boundary, not a failure. And record the exact version of every tool, because rulesets change monthly and a benchmark without versions is a snapshot of nothing.

Results

Ground truth in this corpus has three populations, not two, and the third is the one that had to be fixed before any of these numbers could be published. Alongside the planted secrets and the decoys there are four indicators: AWS access-key IDs. An access-key ID is a credential identifier, not an authenticator. AWS transmits it in cleartext in the Authorization header of every signed request and records it in CloudTrail, and it authenticates nothing without the paired secret access key: "You must use both the access key ID and secret access key together to authenticate your requests."29

Run #5 counted those four as planted secrets. That was wrong, and it was not a rounding error — it decided which tool came first. They are now scored on neither axis: failing to report one is not a miss, and reporting one is not a false positive. It is tallied separately, because "which tools surface key IDs" is a real question for incident response; it is just not a recall question. The planted total falls from 45 to 41. The corpus files are byte-identical — same HEAD commit — so run #6 measures the same corpus as run #5 against corrected ground truth, not a different experiment.28

What the results show

Read this before the findings

This corpus measures recall well and precision badly. Take the two separately.

Recall is the reliable half: 41 planted secrets with known type, placement and obfuscation, so a miss is unambiguous and attributable. Precision is not. Eighteen decoys is a thin noise floor next to a real repository's millions of candidate strings — vendored dependencies, minified assets, test fixtures, generated code. Five of six tools score above 90 percent precision here. Do not read that as contradicting the 1–75 percent range measured across 818 real repositories in 2023;5 read it as the difference between a clean synthetic corpus and a real codebase. Precision on your own repositories is a number only you can measure.

With that established, eight findings.

1
Confirmed

No single tool is complete. Best recall is Betterleaks at 95.1 percent, then Titus at 90.2, and the rest between 53.7 and 85.4. One planted secret — an OpenAI key split across a string array, joined at runtime, and living only in a commit six deep in history — was caught by nothing. Catching it needs history traversal and resistance to split-string obfuscation, and no tool in the set has both.

2
Relocated

The AWS gap is real, and it is in the secret key, not the key ID. Correcting the ground truth did not delete an AWS finding — it moved it from the half that does not authenticate to the half that does.

On the 40-character secret access keys: Gitleaks 4/4, Betterleaks 4/4, Titus 4/4, detect-secrets 2/4 with one out of reach in history — and TruffleHog 0/4, Kingfisher 0/4. Two tools in the field miss every AWS secret access key in the corpus. That is a more serious result than the one it replaces, and it is structurally explicable: a 40-character base64 string with no prefix, no delimiter and no checksum is precisely the shape a pattern-detector engine has no rule to write, and neither of those two runs a general entropy channel that would catch it by another route. It is the same weakness as finding four, on the credential that AWS itself tells you to protect.

On the AKIA… / ASIA… identifiers, now scored as indicators rather than secrets: Titus reports 3 of 4, and every other tool reports none. That is worth knowing when you configure a scanner — the ID is what you feed to aws iam delete-access-key, so surfacing it shortens response — but it is a design choice about what to report, not a detection capability, and it is no longer allowed to move a recall ranking.

3
Confirmed

The verification trap, demonstrated exactly as predicted. TruffleHog in verified-only mode scored 0 of 41. Every synthetic secret is non-live, so the mode reports nothing — a recall of zero that is not merely wrong but inverted. Its own recommended Action snippet runs this way. Benchmark a verifying tool in verified-only mode against a synthetic corpus and you will conclude it detects nothing.

4
Confirmed

Detector-only engines miss the unstructured, and are the most precise. TruffleHog (53.7 percent recall) and Kingfisher (58.5 percent) miss every generic high-entropy string, every AWS secret access key, the headerless PEM body, and the base64-wrapped blob — and they post the highest precision in the field at 100 and 96 percent.

The pattern is sharper than "no entropy channel", which is what an earlier version of this section claimed and the per-type data does not support. Both tools handle postgres and mongodb URIs correctly — 3 of 3 between them — and Kingfisher catches the JWT. What they miss is credential material with no recognisable shape: a bare 40-character base64 string, a hex blob, a PEM body stripped of its armour. A connection URI has a scheme and a user:pass@host structure to key on; an AWS secret access key has nothing. That is a coherent design position for a precision-first engine, and it is the precision/recall trade from section one visible in a single run.

Worth noting against the other direction: the tool that misses the postgres and mongodb URIs on its stock ruleset is Gitleaks (0 of 3), which is neither detector-only nor short of an entropy channel. Part three's regression suite found the same gap in a configured gate and closed it with a custom rule.

5
New

Test-mode Stripe keys split the field, which has a direct bearing on corpus design. On sk_test_… keys: Gitleaks, Betterleaks and Titus each 2/2; TruffleHog and Kingfisher each 0/2. The regex-rule tools match the test-mode prefix; the detector engines appear to gate on sk_live_. The advice earlier in this section to prefer provider test-mode formats for safety is still right, but note the interaction: a corpus built only from test-mode keys will under-report the recall of tools that only look for live ones.

6
Confirmed

Nested encoding defeats most of the field. The base64-blob placement — a key wrapped in an export statement, then base64-encoded — was caught only by Gitleaks and Betterleaks. Four of six tools missed it. Only the Gitleaks lineage decodes and re-scans base64 payloads here.

7
New

detect-secrets buys recall with noise, and none of the noise is invented. 73.5 percent recall on the placements it can reach, at 65.8 percent precision — 25 true positives against 38 findings, the lowest in the set. It emits 13 false-positive findings, every one of them on planted decoy content, resolving to 10 distinct decoys: git SHAs, a base64 PNG, the literal string changeme, ${VAR} placeholders, the provider documentation samples. The remaining three are a second or third rule firing on a decoy another rule already matched, which costs a triager three extra rows to close and is not a separate mistake. Nothing spurious — and that holds field-wide, not just here: across all six tools, every false positive in the run is one of the 18 decoys. Entropy plus keywords casts a wide net; the net caught exactly the things planted to test it. Its 7 history and branch findings are correctly scored N/A rather than misses: it does not walk history by design, and scoring that as failure would be a category error.

The reading that matters is that precision here is a measurement of the decoy set, not of a real repository. Eighteen decoys is a thin noise floor. A tool that scores 65.8 percent against eighteen curated lookalikes will not score 65.8 percent against a vendored node_modules.

8
Practical

The jwt.io sample token is the universal false positive. The demo token pasted into countless READMEs fired on five of six tools — everyone except TruffleHog. If you are starting an allowlist, start there.

The checksum experiment: partially answered

The corpus plants five checksum-bearing GitHub tokens: three with a correct CRC32, two deliberately broken. A checksum-aware tool should reject the broken pair; a regex-only tool should flag both.

A ground-truth ambiguity worth naming, because it is the same class of error as the AWS one. The two broken tokens are planted as secrets, but a token with an invalid CRC32 cannot authenticate anywhere — it is a detector-challenge fixture, not a credential. A tool that validates the checksum and correctly declines to report it would be scored here as a false negative, which would be wrong. In this run the question is moot: all six tools reported both broken tokens, so nothing is being penalised. It stops being moot the moment a checksum-validating tool enters the field, and at that point the two fixtures should move to their own ground-truth class rather than counting against recall.

The published run does not break the pairs out, because the scorer aggregates by secret type and both members of a pair share one. What can be inferred is narrow but real: neither broken-checksum token appears in the caught-by-nothing or caught-by-one-tool lists, so at least two tools reported each. Checksum validation is therefore not suppressing them across the board — but which tools validate and which do not needs a per-secret query against the run's results.json, not the summary. It is the most obvious next thing to publish, and until it is, the checksum question stays open.

Section five · Prior evidence

What the peer-reviewed numbers already say

The benchmark above is one run against a small synthetic corpus. The ESEM 2023 study by Basak, Cox, Reaves and Williams at North Carolina State University is the opposite — nine tools across 818 real repositories and 97,479 manually labelled candidate secrets.5 It is three years old and predates several tools in the current landscape, but on scale and realism it remains the stronger evidence, and reading the two together is more informative than either alone.

Three things to take from that table, none of them the obvious one.

  • No tool achieved both. The highest-precision tool found 6 percent of the secrets. The highest-recall tool was wrong more than half the time. Five of the nine scored under 7 percent precision.
  • The tools disagree profoundly. Gitleaks and TruffleHog each reported over 600 unique true positives the other missed entirely. The authors' conclusion is unambiguous: this demonstrates "the necessity of not relying on a single tool to identify all the secrets."5
  • The failure modes are named and specific. False positives come from "employing generic regular expressions and ineffective entropy calculation." False negatives come from "faulty regular expressions, skipping specific file types, and insufficient rulesets."5 Every one of those is a property of how the technique works, not a defect a vendor will patch away.

Where the two datasets agree, and where they do not. Both find that no tool is complete, and both name the same failure modes — generic regexes, weak entropy handling, missed file types. The 2026 run reproduces the precision/recall trade cleanly: the two most precise tools are the two with the worst recall.

They diverge on two things, and in both cases the newer run is the weaker evidence. On precision, the synthetic corpus is far too clean to be comparable, as the caveat above says. On complementarity, the 2023 finding of 600+ unique true positives in each direction did not reproduce: in the 2026 run no tool had a unique catch. That may be genuine convergence in the field — several of these tools now share a rule lineage — or it may be that 41 planted secrets is simply too small a sample to surface disagreement that a corpus of 15,084 makes visible. The honest reading is that the case for layering is narrower than the 2023 study implies, not that it has gone away.

One more bound on all of this, because it is the easiest conclusion to over-read. Betterleaks catching everything Gitleaks catches, on this corpus at these versions, establishes no detection loss on this corpus at these versions. It does not establish that a Gitleaks pipeline can be swapped for a Betterleaks one without cost. This benchmark measures detection and nothing else: not configuration compatibility, not baseline and allowlist migration, not output format handling in whatever consumes the report, not exit-code semantics, not action and integration availability, not ruleset maintenance cadence, not project maturity, not the governance and audit-evidence questions part four is about. A recall table is an input to a tool decision, not the decision. The place to test the rest is a pilot on your own repositories, and — for the parts that are about your own configuration rather than the tool's — the configured-control regression suite described in part three.

Vendors are aware of the precision problem and are working on it: GitHub reported a 75.76 percent reduction in false positives in June 2026, framed explicitly around trust — "when alerts feel noisy, developers spend more time triaging and less time fixing real issues."27 Note that this is a relative reduction against their own prior baseline; no absolute false positive rate is published.

Section six · Conclusion

Can any scanner reach 100 percent detection?

Answer

No. Measured, on the adjusted count: best single-tool recall 95.1 percent, all six tools together 40 of 41, and one secret that nothing caught. The limit is in the problem, not in the products.

Five structural reasons, in descending order of how permanent they are. Reasons 1, 2, 4 and 5 have direct support in the run above.

Reason 1 · Permanent

"Is this string a secret" is not decidable from the string

A forty-character hexadecimal value is a password, a git SHA, a content hash, or a test fixture, and the string itself does not say which. Structured formats are detectable because a provider chose to make them so. Everything else is inference. No amount of model improvement makes an undecidable question decidable — it only shifts where the errors land.

Reason 2 · Permanent

Precision and recall trade against each other

Widening the rules to catch generic secrets widens the false positive channel by the same mechanism. The 2023 data shows this cleanly: 75 percent precision at 6 percent recall, or 88 percent recall at 46 percent precision. A tool claiming both is either measured on a corpus of only structured secrets or measured against its own ruleset.

Reason 3 · Structural

The format surface changes faster than rulesets

Every new AI service ships a new key format. GitGuardian found eight of its ten fastest-growing detector categories tied to AI services in 2025.2 A detector exists only after someone writes it, which means there is always a window in which a new credential type is undetectable by every tool simultaneously.

Reason 4 · Structural

Obfuscation defeats pattern matching trivially

Concatenating a key across two string literals, base64-encoding it, or splitting it into an array defeats most regex-based detectors without any sophistication at all. This is usually accidental — developers do it for line length, not evasion — which makes it common rather than rare.

Measured. The base64-wrapped blob was caught by two of six tools. The one secret that survived every tool and every combination was an obfuscation case: a key split into an array and joined, sitting in history. And Gitleaks and Betterleaks scored 2/3 on history-planted secrets despite traversing history correctly — the misses were the obfuscation, not the traversal.

Reason 5 · Addressable

The scanner is pointed at the wrong surface

Even a perfect repository scanner is blind to the 28 percent of incidents originating in Slack, Jira and Confluence,2 and to container layers, CI logs, IaC state and MCP configuration files. This one you can fix, by buying coverage of those surfaces. The other four you cannot.

What follows from that is a different posture rather than a different purchase.

  • Run a second tool only if you can name what it adds. This recommendation comes out of the new data much weaker than it went in, and the honest thing is to say so. The 2023 study's 600-unique-true-positives result did not reproduce at all: once AWS identifiers are excluded, no tool in the 2026 field had a unique catch, and the whole six-tool union reached 40/41 against a best single tool of 39/41. One secret. On this corpus, adding five scanners to Betterleaks bought one additional finding and five triage queues. Two readings are available and I cannot separate them: the field may genuinely have converged, several of these tools now sharing a rule lineage; or 41 planted secrets may be too small a sample to surface disagreement that a corpus of 15,084 makes visible. Either way the practical instruction is the same — do not add a second scanner on principle. Measure what your first one misses on your own corpus, and add a second only when you can name the category it covers.
  • Check for detector-level dominance before adding, and be willing to remove — but do not confuse that with a migration case. In this run Betterleaks caught every secret that Gitleaks, Kingfisher and TruffleHog caught, plus more. What that supports is narrow: no recall loss relative to Gitleaks, on this corpus, at these versions. It is not a recommendation to switch. A production migration also spends configuration compatibility, mature CI integration, redaction behaviour, SARIF and reporting expectations that downstream systems depend on, team familiarity, maintenance and stability confidence, and an established exception and governance workflow — none of which a 41-secret synthetic corpus can measure. Part three is where the configured pipeline gets built and regression-tested; part four is where it gets governed. Detector recall is one input to that decision and rarely the decisive one. Run the comparison on your own corpus; a tool that adds no unique catches is adding triage load, and that is a reason to examine it, not to rip it out.
  • Treat scanner output as a sensor reading, not a control outcome. The scanner's job is to point the revocation pipeline. Measure it on time-to-revocation, not on findings volume.
  • Assume a non-zero miss rate and design for it. Since some secrets will always reach production undetected, the controls that matter are the ones that reduce what an undetected secret is worth — short lifetimes, tight scoping, workload binding, and monitoring of credential use, in combination. Note the phrasing: a short lifetime removes persistence and shrinks the replay window, not initial impact. Fifteen minutes is ample to exfiltrate data or mint a second credential. And keep two things separate — workload identity federation removes the standing credential from the runner, but the token it issues is usually still a bearer token; only a sender-constrained credential (mTLS, DPoP) makes the stolen string itself unusable. This is the ladder in Part 1, and it is why scanning sits at tier four rather than tier one.
  • Benchmark against your own estate, and re-run it. Vendor detector counts describe the vendor's coverage of the world. Only your own corpus describes their coverage of you — and a result from a year ago is stale in both directions, which is why the benchmark above runs monthly and prints its own staleness warning. Fork it, add the credential formats your estate actually uses, and read the per-type table rather than the headline F1.

Where the scanner should be installed, and what that pipeline looks like as running configuration rather than a diagram, is the subject of Part 3. What it lets you claim to an auditor, and what it costs the developers who live with it, is Part 4.

Assumptions, sourcing, and confidence

Established. Precision and recall figures are from a peer-reviewed ESEM 2023 study with a manually labelled corpus. Licences, pricing and tier boundaries were verified against each project's own repository, licence file or vendor documentation as of August 2026.

Explicitly unverified — check before relying on it. Whether GitGuardian's free Starter plan permits ggshield in CI (two primary sources conflict). Snyk free-tier limits and whether Snyk Secrets is included. Whether Bitbucket Cloud has native, non-Pipelines secret scanning and on which plan. The exact published rule counts for Gitleaks, Betterleaks and Kingfisher, none of which publish a figure. The maintenance status of git-secrets, which is not archived but appears dormant.

Dated. The ESEM 2023 numbers predate Betterleaks, Kingfisher, Titus and every AI-service credential format. Treat them as evidence of the shape of the problem, not as a current league table.

Limitations of the benchmark in section four. One run, one seed, 41 planted secrets, 18 decoys and 4 indicators. That is enough to measure recall attributably and far too little to measure precision meaningfully — a real repository's noise floor is orders of magnitude larger, which is why five of six tools score above 90 percent precision here and between 1 and 75 percent on 818 real repositories. The checksum experiment is planted but not broken out in the published scoring. Rulesets drift monthly, so any snapshot ages quickly. Treat the run as a reproducible measurement of one corpus, not as a league table.

Known defect in the corpus, unfixed at the time of writing. Four planted "secrets" are AWS access-key IDs, which cannot authenticate on their own and should not be scored as credentials. Section four gives the recomputed figures; the ranking flips, no tool retains a unique catch, and the case for layering weakens to a single secret. The adjusted numbers are my arithmetic on the published per-tool totals, not a re-run — detect-secrets could not be recomputed at all, because the published summary does not say which side of the identifier split it fell on. Until the corpus reclassifies identifiers as locator signals and the run is repeated, treat every recall figure in this section as provisional.
