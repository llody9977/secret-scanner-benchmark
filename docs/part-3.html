The Governed Pipeline

Part two chose a scanner. This is the part where it becomes a control: five control points, each with an owner, a failure behaviour and a bypass authority — and a test suite that proves the configuration still works.

Part 3 of 4 · Implementation Reference implementation current to August 2026 ~6,100 words · 28 min

Executive summary

  1. Roll out server-side push protection first, and alone if you can only do one thing. It is the only control point in this article that stops a secret before it reaches a server other people can read. Everything else in the pipeline is detection, however fast it runs, and should be described that way.
  2. Every control point needs six things named before it is a control: control type, configuration owner, failure behaviour, bypass authority, evidence produced, response owner. A scanner with none of those is a script. The table in section two fills them in for all five.
  3. The three-outcome rule is the implementation detail that decides whether any of this works. A scan has three results — clean, findings, and did not run — and pipelines that collapse the third into the first report green while covering nothing. Every workflow here validates that a report exists and parses before believing a zero.
  4. Never republish what the gate caught. A job summary has wider read access than the branch the secret came from. Redaction is verified before any summary is written; an unredacted report fails the run.
  5. A configured gate is not self-verifying. A rule that stops matching fails silently and looks exactly like a clean repository. The configured-control regression suite — 21 scenarios, 16 must-block and 5 must-pass — is what makes that failure loud.
  6. It found two gaps the first time it ran, on classes this repository claims to care about: a PostgreSQL URL with an inline password, and an HTTP Basic header. Nobody discovers a missing rule by rereading the rules they already have.
  7. The hosted push-protection test is the series' one positive case. A non-issued Mailchimp-shaped fixture was rejected at push, bypassed with a logged reason, and produced an alert.1 That is prevention, demonstrated rather than claimed — and the bypass record is the control, not the hole in it.
  8. This whole control set assumes every deployable change reaches production through the enforced repository and pipeline path. Where production can also change by manual deployment, an admin console, direct registry publication, CI variables or break-glass, the repository control covers one route of several. The testable principle is coverage of every production ingress path — and automating the pipeline does not by itself achieve it, because an automated pipeline still injects values that were never in the repository.
  9. Static scanning cannot reach runtime credentials at all — stolen session cookies, tokens in process memory, values from a metadata service. The last section is about making the static surface smaller rather than scanning it harder.
Section one · Sequence

Roll out in this order, and know why

Most secret-scanning programmes are built in the wrong order, and the order is not an accident. Local hooks are easiest to ship, so they ship first; CI scanning is visible to management, so it ships second; push protection requires an administrator and a conversation about bypass policy, so it waits. The result is a programme whose only enforcing control is the one nobody got round to.

The order below inverts that. It is ordered by what each control can prevent, not by what is easy to install.

First · Preventive, enforcing

Git-host push protection

Server-side, pre-receive. It applies to every push from every clone regardless of what any individual developer has installed, and it cannot be removed by the person it constrains. It is the only point at which a secret is stopped rather than found.

  • Enable it repository-wide, not per-user. A per-actor exemption destroys the evidence the control exists to produce.
  • Require a bypass reason from a fixed list. The bypass is the reason developers tolerate the control; the record is the reason governance can rely on it.
  • Accept that its coverage is bounded by the host's patterns — see section five. Enforceable is not the same as complete.
Second · Detective, enforcing at merge

Required CI check for merge and deployment

A full-history scan wired into branch protection as a required status. It does not prevent exposure — the objects are already on the server — but it prevents promotion, which is the next thing worth stopping.

  • Required, or it is advisory. An unrequired check is a notification with a spinner.
  • Full history, not the diff. A shallow clone makes this job pass on a repository whose secret is one commit back, and it passes quietly.
  • This is where your custom internal formats get enforced, because the host almost certainly does not know them.
Third · Detective, no critical path

Scheduled history and wider-source discovery

A weekly full-history scan with a broader detector set and a lower confidence threshold, plus discovery on the surfaces that are not repositories at all. Nobody is waiting, so this control can afford breadth that would be intolerable at a gate.

  • Different tool, deliberately. Gate tools optimise for precision; discovery tools should optimise for reach. Part two measured the difference rather than assuming it.
  • Catches the pre-existing exposure — everything committed before the gates existed, which is the majority of what a new programme finds in its first month.
  • Findings go to a triage queue with an owner, not to a pull request.
Last · Preventive, advisory

Local hooks, optional by design

Fast feedback on the developer's own machine, before the commit exists. Genuinely valuable, and genuinely worthless as a control: it is opt-in, bypassable with --no-verify, and evidences nothing.

  • Ship it as a convenience with an honest description. A local hook presented as a control is the most common overclaim in this family.
  • Its real value is economic: failing in two seconds locally rather than two minutes into a pipeline is the difference between a fix and a bypass request.
  • Run the pre-push hook against full history, not staged content. What reaches the server is the history.
The sequencing test

If you can install exactly one of these this quarter, install the first. If a programme has the last three and not the first, it has bought thorough observation of exposures it could have prevented — and it will report a rising detection count as evidence that it is working.

Section two · Definition

Five control points, fully specified

A scanner becomes a control when six questions have answers. Most implementations answer two — what it scans and what it reports — and discover the other four during an incident or an audit, which is the expensive time to discover them.

Each control point, and the six things that make it a control rather than a script
Control point Control type Configuration owner Failure behaviour Bypass authority Evidence produced Response owner
Server-side push gate Preventive, enforcing Organisation or repository admin Push rejected; objects never land Pusher, with a reason from a fixed list; logged Block record, bypass record with actor and reason, secret-scanning alert Security engineering, on bypass

Incident-response trigger Corrective Security engineering Incident opened; revocation clock starts None — revocation is not optional Incident record, exposure window, revocation timestamp Named owner per credential class

Three columns in that table are the ones that get skipped, and each has a characteristic failure.

Bypass authority. A preventive control with no escape hatch gets switched off within a quarter. A preventive control whose escape hatch is undocumented and unlogged is theatre. The only version that survives contact with delivery is one where bypass is available, attributable and counted — and where the count is a reported metric rather than an embarrassment. Part four treats the bypass rate as a primary governance number for exactly this reason.

Response owner. Not the team that runs the scanner. The team that owns the credential, per class, by name. The measured failure across the industry is that findings do not become revocations, and unowned findings are where that failure lives.

Evidence produced. Decide this before an assessor asks. "The scanner runs" is not evidence; a check run with a retained job summary and a bypass log is. Note also what is not evidence: a clean scan means the configured detectors did not match, which is a statement about your ruleset and not about your repository.

The fifth row is the one most implementations lack entirely. A finding that does not automatically start a revocation clock with a named owner is a ticket, and part one has the number for what happens to those.

Section three · Reference implementation

What this looks like as running configuration

Everything below is in llody9977/secret-scanner-benchmark and runs on every push.2 It is GitHub-specific in its syntax and not in its structure; the four decisions that matter port to any host.

One thing to establish before the configuration, because it is the most common way to get this wrong at the design stage: the gate's ruleset and the benchmark's ruleset are different artifacts and must stay that way. The benchmark in part two runs every tool stock, because a benchmark against a tuned configuration measures the tuning. The gate runs a configuration tuned hard for this repository, because a gate that has not been tuned to the formats you actually have is covering someone else's threat model. Merging them produces a number that is neither a measurement nor a control.

The gate's ruleset

Three decisions, in controls/gitleaks.toml:

  • Extend the provider defaults; never replace them. [extend] useDefault = true. A local ruleset that replaces the defaults is the most common way a gate silently stops covering the formats it was installed for — and it fails clean, so nothing surfaces it.
  • Add the formats only you have. The internal token shape that no vendor ships a detector for is, definitionally, the one where a silent regression is invisible. It is also usually the one with no provider revocation programme behind it, so a leak of it is entirely your problem.
  • Allowlist by path, narrowly, with a written reason. This repository allowlists the generated benchmark corpus, the regression templates, and six named generator modules — not ssbench/, so a secret committed anywhere else in the package is still caught. An allowlist entry without a reason becomes permanent; an allowlist entry that is a directory becomes a hiding place.

Four implementation decisions that decide whether it works

1
Exit codes

A scan has three outcomes, not two. Clean, findings, and the scanner did not run. Collapsing the third into the first is the single most common way a pipeline reports green while scanning nothing: a release download that 404s, a config path that moved in a refactor, a timeout on a large history, an archive whose checksum silently changed.

The workflow treats exit 0 as clean, exit 1 with a parseable report containing findings as a failure, and everything else as an error that fails the job. It validates that the report file exists and parses as the expected shape before believing a zero. A green check that means "the scanner crashed" is worse than a red one, because it is load-bearing in a control narrative.

2
Redaction

Never let the gate republish what it caught. Scanners are run with --redact=100, and the workflow then verifies that every finding's secret field is empty or redacted before it writes any summary. An unredacted report fails the run rather than being published.

The reasoning is a read-access one. A job summary, an artifact and a SARIF upload all have wider and longer-lived read access than the branch the secret came from. A gate that writes the matched value into job output has not reported an exposure; it has created a second, more accessible copy of it, and one that outlives the branch deletion.

3
History depth

fetch-depth: 0, and persist-credentials: false. The first because what reaches the server is the history, not the working tree — the benchmark plants secrets in a reverted commit and six commits deep precisely because that is where real ones are found, and every history-capable scanner finds them. A shallow clone makes the job pass on a repository whose secret is one commit back.

The second because a scanning job has no need for a token in the runner environment, and part one's third case study is what happens when a job that did not need a credential had one anyway.

4
Pinning

Pin the version and verify the archive. Every tool is pinned to an exact release and its download is checked against a recorded SHA-256 before it is executed. Pinning a version tag alone still trusts whatever that tag points at today.

Actions are pinned to release tags here for readability; in production, pin each to its 40-character commit SHA. Part one's Shai-Hulud case turned on an unpinned third-party action, and a security-scanning workflow is a particularly attractive place to put one, because it runs on every push and nobody reads its diff.

The remaining choices are smaller but worth stating. Output format: JSON for the gate, because the workflow needs to count and group findings by rule and to verify redaction; SARIF where a code-scanning UI consumes it. Corpus exclusions: both test populations are excluded from the gate's own scan, because neither is a finding about this repository — and, more importantly, the generated corpus is never committed at all, so the exclusion is a backstop rather than the mechanism. Verification: disabled everywhere in this repository. No candidate from a scan is sent to an issuing provider, and part two's verified-only row shows what happens when verification is treated as a scan filter rather than a triage input.

Section four · Verification

The configured-control regression suite

The problem this solves

A configured gate is not self-verifying. A rule that stops matching — because a ruleset update changed a detector, because an allowlist path grew, because someone replaced useDefault with a bespoke set — fails silently, and a broken gate looks exactly like a clean repository. Both produce a green check and zero findings. Nothing in the pipeline distinguishes them.

So the repository carries two test populations, deliberately separate, answering different questions. Conflating them is the mistake this section exists to prevent, and it is easy to make because both are corpora of fake secrets.

Two corpora, two questions. A number from one is meaningless in an argument about the other.
Comparative benchmark corpusConfigured-control regression corpus

OutputPrecision, recall, F1, cross-tool coveragePass or fail, per control decision

A failure meansInteresting. Write it up.Something is broken. Fix it today.

The regression suite asserts one thing per scenario: the control decision. Sixteen credential classes must block; five inputs must pass. Detector names and finding counts are recorded but not asserted — detector names change between releases, and pinning them produces failures that teach nothing and get muted within two version bumps. The record exists so a reviewer can diff detector attribution across an upgrade and see how the gate reached the same decision, which is often where a coming regression is visible first.

One further assertion sits outside the decision: any report the gate produces must be fully redacted. That is checked per scenario, because it is the property most likely to regress unnoticed when someone adds a flag.

The five must-pass scenarios are the ones that keep the gate usable. A runtime secret reference, a documentation placeholder, an SSH public key, a connection string with an interpolated password, and a bare AWS access key id. A ruleset change that improves coverage by breaking one of those has not improved anything — it has moved cost onto every developer who writes a config file, and bypass requests are how that cost gets paid. Part four has the friction evidence; this is where the friction budget is actually spent or saved.

The access key id case connects directly to part two. A bare AKIA… with no secret access key near it does not block, and that is specified behaviour rather than a gap: an access key id is an identifier AWS transmits in cleartext in every signed request,3 so blocking a push on one costs a bypass request and prevents no exposure. It is the same distinction the benchmark scores as an indicator — asserted here as a control decision instead of measured. The trade-off is real and named in the manifest: the id is what incident response feeds to aws iam delete-access-key, so an organisation that wants key ids surfaced should route them to scheduled discovery, not to the gate.

It earned its place on the first run

Against the stock provider ruleset plus the internal-format rule, two scenarios failed immediately: a PostgreSQL URL with an inline password, and an HTTP Basic Authorization header. Neither is exotic. Both are on the list of classes this repository says it cares about. Nobody had noticed, because nobody discovers a missing rule by rereading the rules they already have.

The benchmark had already reported the same weakness from the other direction — Gitleaks misses the postgres and mongodb URI cases on its stock ruleset. That is the intended relationship between the two populations: the benchmark tells you where the product is weak; the regression suite is where you do something about it and keep it done.

Then the fix produced its own defect. The first version of the connection-string rule fired on postgres://user:${DB_PASSWORD}@host — the interpolation template, which is the pattern developers are being asked to adopt. A gate that blocks the correct answer teaches developers the gate is wrong, and that lesson is not unlearned. The rule now excludes interpolation forms and a must-pass scenario pins it. Every new rule needs its negative case on the same day, or its precision cost is discovered by a developer instead of by a test.

A last detail that is not incidental: no credential-shaped string is committed. The regression templates hold {{PLACEHOLDER}} tokens; values are fabricated from a committed seed and materialised into a temporary directory only for the duration of the scan. This repository is public, forked and mirrored, and a checked-in file full of credential shapes is a push-protection and secret-scanning landmine for everyone downstream. It is not obfuscation — every value is worthless — it is declining to make your test fixtures into other people's alerts.

Section five · Evidence

The one time scanning actually prevented the exposure

The server-side push gate is the only preventive control point in the set, and the only one that cannot be tested with a CLI. It is a host feature. The only way to know what it does is to push at it and record what happens.

So that is what was done, in this repository, on 30 August 2026: a deliberate push of a non-issued, Mailchimp-shaped fixture at a repository with GitHub secret scanning and push protection enabled, then a documented bypass, then the resulting alert.1 The fixture is generated from the committed seed by the regression suite, so the value in the test and the value the CLI gate sees are the same value.

Two things are worth reading twice.

The push was stopped before the object reached a server anyone else could read. Not detected, not alerted on — stopped. Nothing downstream of a push can do that, however fast it runs. This is the distinction the series keeps insisting on, and this is the one place in four articles where it is demonstrated rather than asserted.

The bypass is the control, not the hole in it. The push succeeded on retry, because a developer with a legitimate reason could give one. What matters is that the bypass produced a durable record naming the actor, the reason and the commit. Judge this control by whether its bypasses are attributable and counted, not by whether they exist.

What this result does not say

It is one provider-pattern scenario, not a detection rate. It says nothing about the other twenty scenarios in the regression corpus, several of which are generic or internal shapes.

The tested repository was public and personal. Provider-pattern scanning and push protection were on; non-provider generic patterns, validity checks and repository custom patterns were unavailable or off — the custom-pattern endpoint returned 404. An eligible organisation on a paid secret-protection plan gets generic detection, AI-assisted detection, validity checks and custom patterns, none of which were exercised. Assess those on your own plan; this is neither a ceiling nor a floor for them.

The fixture was never issued and validity checks were disabled. The result records pattern classification and push behaviour, not credential validity.

One format, one run, provider checks off. Detection claims belong in part two, against a corpus built for them.

The fixture value changed the result

An earlier run of this same experiment, in the predecessor repository on 25 August 2026, recorded TruffleHog as not detecting this fixture. The re-run detects it. TruffleHog did not change — the version is identical. The fixture value did.

The old fixture used a sequential low-entropy placeholder of the correct shape. This repository generates the value from a committed seed, so it is random hex of the same shape. Side by side, at the same version: sequential value, 0 findings; random value, 1 finding. TruffleHog is filtering the placeholder, not failing to match the pattern — so the earlier result measured the tool's placeholder filter rather than its detector.

This is the same class of error as the AWS access-key-id correction in part two: a property of the corpus, read as a property of the tool. Stated as a rule for anyone building fixtures — a fixture that looks like a placeholder will be treated as one, and a corpus of hand-typed 0123456789… values systematically understates every tool that filters them. Generate from a seed; do not type a pattern by hand.

The general lesson is about the boundary between host-managed and repository-managed rules. The formats only you have are the formats the host is least likely to cover, and they are usually the ones with no provider revocation behind them either. Host patterns cover the vendor formats well and are maintained for free; your internal token shape is yours to detect, at the pull-request CI gate, in a ruleset you version and regression-test.

For every format the host does not block, choose one explicitly and write down which: accept the gap as a recorded risk with an owner; cover it at the CI gate and accept that the control is now detective for that format rather than preventive; or remove the need for the format to exist, which is the next section.

Section six · Response

Deleting the line is not revocation

A later commit that removes the value does not remove the earlier git object. The value may still be in local clones, remote branches, pull-request refs, forks, caches, build output, logs, artifact storage and backups. History rewriting can reduce future exposure; it cannot make a value that was copied unknown again.

The benchmark makes the same point structurally: two of its placements are a secret committed and then removed in the next commit, and a secret six commits deep that is gone at HEAD. Every history-capable scanner finds them. So does everyone else's.

The order below is deliberate. Revocation precedes repository cleanup, which is also where GitHub's own history-cleanup guidance puts it.4

1 · Immediately

Revoke or rotate

Invalidate the credential at its issuing system before touching the repository. Everything else on this list is slower and none of it shortens the window. Where auto-revocation is too risky, rotate: issue the replacement, cut consumers over, then invalidate. Rotation with a gap is an outage; rotation without invalidation is not rotation.

2

Establish the exposure window

First commit containing the value; every branch, tag, fork and surface it reached; who and what could read those; and the time revocation actually completed, not when it was requested. The window runs from first push to completed revocation, and it is the interval you investigate.

3

Investigate use

Provider, identity, cloud, database, CI and application logs, inside that window. Scope to the permissions the credential actually had, which for a long-lived unaudited key is usually wider than assumed. Absence of evidence in a log you do not retain is not evidence of absence — establish retention before concluding "no use".

4

Replace the storage pattern

Move to a secret manager, or better, remove the stored value entirely. A rotation that puts the new value back in the same file has bought one cycle. This is the step that changes whether the incident recurs, and the one most often deferred.

5 · Not urgent

Remove from HEAD, then decide about history

Rewriting changes every downstream commit hash, invalidates signatures, disrupts open work, and requires coordination with every clone owner — one stale clone can push the value back. Sometimes right; never urgent in the way revocation is. Treating the rewrite as the emergency is how the first hour gets spent on the wrong task.

6

Search adjacent surfaces

Issues, pull-request descriptions, wikis, chat, CI logs, build artifacts, container layers, package registries, IaC state, MCP configuration, documentation. Part two put 28 percent of incidents in collaboration tools alone — Slack, Jira, Confluence — and no git scanner looks at any of these surfaces. The rest of the list is unmeasured, which is worse than a known number, not better.

7

Add a regression guard

A scenario in the configured-control suite, so the class cannot recur silently: a template with a placeholder, a manifest entry, and a why: naming the incident. Never commit the real leaked value as a fixture — that turns a closed incident into a permanent one, in a file whose whole purpose is to be widely copied.

Section seven · Boundary

What no amount of scanning reaches

The boundary

Repository and artifact scanners do not detect credentials that exist only at runtime: stolen session cookies, tokens scraped from process memory, dynamically minted credentials, values read from an instance metadata service. None of these is ever written to a file a scanner walks. Expanding static scan coverage does not close a runtime-credential gap, and a programme that reports scanner coverage as its credential-risk metric is measuring the surface it can see rather than the one being attacked.

That is not an argument for scanning less. It is an argument about what the pipeline in this article is for, and about where the remaining budget goes once it is built. Three things follow, and they compose.

Repository scanning is only as strong as your production ingress

Everything in sections one to five assumes something that is rarely written down and often false: that all deployable code and configuration reaches production through the enforced repository and pipeline path. The push gate, the CI gate and the scheduled scan sit on that path. They are preventive with respect to that path and blind to every other one.

So the question that decides whether this control set is strong or decorative is not "is our scanner good". It is: how many ways can production change, and how many of them cross a gate? Most organisations, asked to enumerate honestly, find several that do not:

  • Manual deployment — a human running a deploy command, or copying a file onto a host.
  • Administrative consoles — a cloud console, a SaaS admin panel, a feature-flag service, a CDN configuration UI.
  • Direct registry publication — a package or image pushed from a laptop rather than built by the pipeline. This is the path in two of part one's three cases.
  • Manually installed MCP and agent configuration — files that live on a workstation or in an agent deployment and were never in a repository.
  • CI variables and environment configuration — set in a platform UI, versioned nowhere.
  • Out-of-band configuration upload — a config blob posted to an API, a secret pasted into a runtime store.
  • Break-glass procedures — which exist precisely to bypass the normal path, and are the least likely to be instrumented.

Each of those is a route by which a credential can arrive in production without ever passing a scanner. A control narrative that says "all code is scanned before deployment" is making a claim about ingress topology, not about the scanner, and it is the ingress claim an assessor should be testing.

The qualification that catches people out

Automating the pipeline does not, by itself, make repository scanning complete. This is the failure mode of the organisation that has done the work: everything deploys through CI, nothing is hand-copied, and the conclusion drawn is that the repository gate now covers production. It does not, because an automated pipeline still injects values that were never in the repository:

  • secrets read from CI variables;
  • values fetched from a secret store at deploy time;
  • credentials minted at runtime by a workload identity broker;
  • parameters supplied by whoever triggered the deployment;
  • external configuration that is not represented in source control at all.

None of those is visible to a scanner reading the repository, and every one of them is a place a credential can be wrong, over-scoped or exposed. Automation moves the injection point; it does not remove it.

The stronger principle, and the one worth writing into a control narrative because it is testable: coverage of every production ingress path. Enumerate the paths, name an owner for each, state which control acts on each, and accept explicitly that some have none. That list is a governance and architecture artifact, not a scanning one — and it is the thing that determines whether the pipeline in this article is a control or a checkbox.

Make the static surface smaller

Every control in sections one to five is a way of catching a static secret. The alternative is not having one.

  • Workload identity and OIDC federation. A CI job exchanges its own identity for a short-lived cloud token instead of holding a long-lived key.5 This removes the standing credential from the runner, which is precisely the failure mode in part one's third case study.
  • Trusted publishing for packages. The same exchange for a registry: no publishing token in the runner environment at all. Given that a stolen publishing token is how two of part one's three cases proceeded, this is the highest-leverage single change available to most projects.
  • Dynamic, short-lived credentials. Minted per job, expiring in minutes. Keep the claim honest, though: a short lifetime removes persistence and shrinks the replay window; it does not remove initial impact. Fifteen minutes is ample to exfiltrate data or mint a second credential.
  • Sender-constrained tokens. The one that changes the shape of the problem. Workload identity still usually issues a bearer token — whoever holds the string can use it. mTLS-bound or DPoP-bound tokens6 are cryptographically tied to the client, so a copied string is not usable by the copier. This is the only item on the list that makes the leak itself inert.

Each of these reduces the number of things the pipeline has to catch. A format that no longer exists as a static value cannot be missed by a scanner, cannot be scored in a benchmark, and does not need a regression scenario.

Detect what static scanning structurally cannot

For the credentials that remain — and for the entire runtime class that was never in a file — the detection surface is telemetry, not source:

  • Identity telemetry. Anomalous token use: impossible travel, unusual ASN or geography, a workload calling an API it has never called, a credential used outside its normal hours or from outside its normal network.
  • Workload telemetry. Egress from a workload to an endpoint it has no reason to reach; a process reading a credential store it does not own; a container making its first outbound connection.
  • Endpoint telemetry. Process-level access to browser cookie stores, keychains and credential caches — the acquisition path for the runtime class that never touches a repository.
  • Credential-use monitoring at the provider. The only signal that answers the question incident response actually has, which is not "was it leaked" but "was it used".

These are different teams, different budgets and a different article. The point of naming them here is scoping: a credible credential-risk programme reports on both surfaces and does not let coverage of the cheap one stand in for coverage of the expensive one. Part four is about what you can honestly claim, and this is the claim most often overstated — a scanner coverage percentage presented as a credential-risk percentage, in a control narrative that never mentions the surface it cannot see.

Assumptions, sourcing, and confidence

Reproducible. Every configuration, workflow and test in sections three and four is in the repository and runs in CI. The regression suite's result — 21 scenarios, 16 blocked, 5 passed, 0 deviations — is reproducible with python regression/run.py against Gitleaks 8.30.1. The two gaps it found on first run, and the precision defect in the first version of the connection-string rule, are recorded in the commit history rather than reconstructed.

Directly observed. The hosted push-protection result in section five was produced by an actual push at this repository on 30 August 2026, with the alert retrieved from the alert API and only sanitised metadata retained — the API returns a secret field, which is deliberately not copied. The block, the bypass, the retry and the alert are all this repository's own result, reproducible by the procedure published alongside it. An earlier run of the same experiment in the predecessor repository is retained as provenance.

Judgement, not measurement. The rollout order in section one, the six-column control specification in section two, and the split of tools between gating and discovery are engineering positions. They are defensible from the evidence in parts one and two, but they are not measurements and another team could order them differently with good reasons — particularly an organisation whose host offers no push gate at all, where the CI gate has to carry weight it is not designed for.

Out of scope. Section seven names the runtime-credential surface and the architectural options that shrink the static one. It does not evaluate any of them. Workload identity, sender-constrained tokens and runtime telemetry each deserve their own treatment, and nothing here should be read as an implementation recommendation for a specific product.

Platform specificity. The reference implementation is GitHub Actions. The four decisions in section three — three-outcome exit handling, verified redaction, full history, pinned and checksummed tools — are host-independent. The syntax is not.
